Sail Insight · UX & network audit

A smoother day on the water

Clearer failures, safer organizer workflows, consistent boat controls, and diagnostics that users can copy. The Android tests drive the real app against a real Sailing Analytics test server, including a complete regatta on two phones.

qa/ux-network-auditAndroid API 36 · Maestro

This branch follows a sailing day: sign in, prepare the regatta, join with a boat, track, and archive. The improvements below retain the app’s existing workflows while correcting failures that were silent, misleading, or left an operation stuck.

Status: checked on 12 October 2026. All 28 Android E2E tests passed against a freshly started test server, and the two-phone regatta passed with the correct result on the server. Details in Latest results. Still open: a run on GitHub Actions and the decisions in chapter 8.

1 · Signing in: explain what actually failed

A lost connection should not look like a bad password. A failed reset request should not promise an email.

Bug fixed

The form stays usable when the network is gone

Login now distinguishes incorrect credentials from connection failures. The error appears beside the action instead of silently doing nothing. Loading state is released after failure, so the user can retry.

Implementation: the screen uses the actual failure type and status. A synchronous pending flag also prevents the keyboard and button from starting two requests before React updates the loading state. This narrow timing race is covered by a code-level test, because a UI test cannot tap twice within the same few milliseconds reliably.

E2E test: auth-login-offline enables airplane mode, submits, checks feedback, then restores connectivity.

Bug fixed

No false “check your inbox”

Password reset now waits for the request. A transport or server failure releases the button and reports the problem. The existing generic confirmation for an unknown account is retained, so the screen does not disclose whether someone has an account.

E2E test: auth-password-reset-offline. A code-level test additionally covers the double-submit race.

2 · Preparing a regatta without losing the organizer’s work

The form should reveal the field that needs attention. Saving a course and changing race counts should leave server and screen in agreement.

UX improved

Show the problem where it can be fixed

Submitting an incomplete event scrolls toward the invalid section. The missing venue is marked directly below its field. Backend failures likewise scroll into view rather than staying below the keyboard or screen edge.

Implementation: section positions are measured by the existing form. Discard thresholds must be ordered; boat and event required fields reject whitespace-only input.

E2E test: create-event-validation checks missing venue feedback.

UX improved

The keyboard no longer hides the choice

Focusing the boat-class field scrolls it upward and reserves enough space for the suggestions. Create Event reuses the list it already fetched rather than asking the same input to fetch it again.

Evidence: this recorded Android checkpoint shows all five suggestions above the keyboard. The test checks that the suggestion can be tapped; it does not measure pixel positions.

Bug fixed

A failed create is not a stuck spinner

The create state is cleared on failure. If the server created the event but a later setup step failed, the app distinguishes that partial result from a failed creation, reducing the risk of creating a duplicate on retry.

Verification: create-event-offline checks connection feedback and recovery. The case “event created, but a later setup step failed” is covered by a code-level test, because the test server cannot be made to fail exactly that one follow-up request.

Bug fixedUX improved

Race-count changes are deliberate and ordered

Reducing the count names the races that will be permanently deleted. Rapid changes are queued and calculated against refreshed server state, rather than repeatedly using an outdated local count.

Implementation: overlapping settings saves are counted, so one completed request cannot re-enable controls while another is still running. Tracking starts after settings are saved. define-races checks adding, cancelling deletion, confirming deletion, and reopening the overview; rapid repeated changes and partly failed server writes are covered by code-level tests.

Bug fixed

Save means the course can be reopened

The editor starts and stops local location updates on focus. Ping rejects missing or non-finite coordinates instead of submitting an empty position. Manual degrees/minutes input is checked against coordinate bounds.

Repeated Save presses no longer create duplicate courses. Copying the saved course to following races is separate from the main save; a partial copy failure gets a partial-success message, not an unqualified success.

E2E test: define-course pings, saves, and reopens the course. The GPS position is simulated by the emulator; real-world GPS accuracy is not tested.

Bug fixed

Typed mark positions stay as typed

Organizers can type a mark position in degrees and minutes instead of pinging it. On main, the map moved to the typed position and then wrote its own, slightly different center back into the fields: 20.880′ became 20.877′, and a field could change while the organizer was still typing. Now only dragging the map changes the numbers.

Correcting a value also kept old digits: the cursor landed in the middle, so typing “12” over “12.360” gave “120”, which is then rejected. Tapping a field now selects its value (highlighted in yellow), so typing replaces it. An impossible position such as 91° N is still rejected and never saved.

E2E tests: course-editing and the regatta type all mark positions and check the saved values exactly.

Bug fixed

An inventory refresh should not undo deletion

The inventory screen reloads without recreating missing default marks. A refused server deletion restores the locally removed item and reports the error. Failed inventory retrieval is not treated as an empty inventory that needs every default recreated.

E2E test: mark-inventory deletes a mark, reloads, restarts the app and checks the mark stays gone. Creating a new course can still bring default marks back; see open decisions.

3 · Joining, tracking, and reporting a problem

Competitor forms stay simple. Technical information stays optional.

Bug fixed

Accept usable boat data, not just nonempty strings

Boat names and sail numbers are trimmed. Required fields reject blank input. Duplicate-name checks account for surrounding spaces and letter case. Handicap validation rejects non-finite and non-positive values.

Deleting after editing a name without saving still targets the original stored boat. A failed deletion is shown rather than leaving the user to guess what happened.

E2E tests: competitor-boat-validation checks invalid then valid boat entry; my-boats checks adding and deletion after an unsaved rename.

UX improved

Use the same button as the rest of the app

The old custom text used different typography and sat too low. NEW BOAT now uses TextButton and the standard primary-button font. Using the shared component keeps typography and vertical alignment consistent with the other actions.

E2E test: my-boats uses this button.

Bug fixed

Start once; report stop failures honestly

Tracking focus handling is idempotent, including the first focus. Repeated actions are guarded, and switching away from another tracked event asks for confirmation. A failed stop no longer displays the event-finished success message.

E2E test: competitor-tracking joins, starts tracking with a simulated GPS position, checks the running timer and stops.

Bug fixed

A failed refresh should not stop later updates

Polling avoids offline requests and resumes after failed or missing responses. A failure streak produces feedback without repeating the same snackbar on every poll.

E2E test: leaderboard opens, switches view and refreshes this screen. Recovery after failed refreshes is covered by a code-level test.

New app behavior

Archiving is reversible

On main, an archived event disappears from the list with no way to bring it back in the app. Now the snackbar offers Undo, and Show archived events lists archived events so they can be restored. If the server rejects the change, the list goes back to its previous state.

E2E test: archive-event archives and restores an event. This is new behavior, so it is listed under open decisions.

UX improvedNew diagnostics UI

Readable first, technical when requested

A real duplicate-event response produces a useful message. Expert users can expand its method, endpoint, status, and backend error code, then copy the details.

E2E test: create-event-error-details checks the message for ordinary users, that expert users can expand and collapse the details, and that copying works.

New app behavior

Give support the error, not a photograph of it

Enable: Account → Settings → tap the version number 15 times → enable Show technical error details. Reproduce the failure, expand Show details, and choose Copy technical details.

Copy local diagnostics copies the app log (see Logs) to the clipboard, so it can be pasted into an email. Nothing is uploaded automatically. When a message has no error details of its own, Details shows the recent log instead and says so, because those entries are not necessarily about this failure.

E2E test: expert-local-diagnostics causes a real failed login, logs in, switches GPS logging on and off (the setting must persist) and copies the log; the copy must contain the failed login.

4 · A complete regatta on two phones

The most important thing the app does: an organizer sets up a race, sailors join, everybody is tracked, and the server produces a result. This test plays it through with two Android emulators and the real Sailing Analytics server, without shortcuts through the API.

New E2E test

Phone A organizes and sails, phone B only sails

Phone A (the run’s account, registered through the app) creates the event, types in the start line (pin and committee boat, 200 m apart) and a windward mark about 900 m upwind, saves the course, sets the start time of R1 and joins the race with its own boat. Phone B has no account: it opens the organizer’s invitation link (the same link the event’s QR code contains), joins with a new boat and starts tracking from the Tracking tab.

Both boats then sail R1 at the same time: across the start line, around the windward mark and back across the finish line. Phone A sails at 9 m/s, phone B at 6 m/s. The positions come from each emulator’s own GPS, one position per second, so the app, its GPS library and the upload work exactly as on the water.

Checked on the server

The server scores the race

After sailing, the test asks the server for the regatta leaderboard and waits until R1 is scored for both boats. Result of the run on 12 October 2026:

Run it: ./e2e/regatta.sh once the test server, Metro and the first emulator are running. It starts a second, disposable emulator itself and deletes it afterwards (or uses E2E_REGATTA_SERIAL_B). Found by this test

What the regatta test uncovered

Typed mark positions changed by themselves (fixed), and corrected coordinates kept old digits (fixed): see Typed mark positions stay as typed in chapter 2.

A far-away first position blocks tracking (open). If the first position after START TRACKING is very far from the next ones, the GPS library rejects all following positions as a “teleport”, and the distance tile shows the jump (here 8,719,855 m). See open decisions.

E2E tests: course-editing types positions, including an impossible 91° N that must be rejected, and checks the saved value exactly.

5 · Logs: what the app records and where to find it

On main the app writes no log file of its own. Only the GPS library keeps a log, and only while GPS logging is switched on. That is why the app’s data folder on the phone was empty. This branch adds an app log that is always on.

What is recorded

  • Every server request: method, address, HTTP status and duration, e.g. API GET …/api/v1/regattas 200 182ms. The one exception is the frequent upload of the sailor’s own GPS fixes; it would flood the log, and the GPS library already records it.
  • Every failed request with the kind of failure (no connection, timeout, HTTP error) and the server’s status.
  • Every error the user sees, both pop-up dialogs and the short messages at the bottom of the screen (snackbars), together with the underlying error.
  • Errors the app handles silently (for example when starting or stopping GPS tracking fails), uncaught program errors, failures of background tasks, and errors during app start.
  • Normal taps and screen changes are not logged; they rarely help with bug hunting and would hide the important lines.

Passwords, access tokens, user names, e-mail addresses, names and device IDs are removed before anything is written. Event, regatta, race and boat identifiers stay in, because support needs them to find the case on the server. Request and response bodies are not logged.

Files are kept for 14 days and limited to 25 MB in total; there is one file per day (sail-insight-YYYY-MM-DD.log).

How to get the log

  1. Copy and e-mail it (any phone): Account → Settings → tap the version number 15 times to open Expert Settings → Copy local diagnostics. Paste it into an e-mail. This copies the most recent 256 KB.
  2. Android, complete files: connect the phone to a computer by USB and open Android/data/org.sailyachtresearch.sailinsight/files/sail-insight-logs/. Note: the app id starts with org., not com.. Many phones (Android 11 and newer) hide the Android/data folder in their own file manager app; on the computer it is visible.
  3. iPhone, complete files: Files app → On My iPhone → Sail Insight → sail-insight-logs. From there a file can be shared like any other document.

Expert Settings shows the matching folder for the phone it runs on. The existing Send log to e-mail button is unchanged. It sends the GPS library’s own log, which contains positions and is not filtered, so the screen shows a warning first. While “Enable verbose background GPS logging” is on, that log also receives copies of app log lines, but it is not a complete copy of the app log.

What does not reach the app log

Native crashes (the app process dies outside JavaScript) and the GPS library’s internal events are not in this file. Crashes go to Firebase Crashlytics as before; the GPS internals are in the GPS log. Crashlytics also receives failed server requests (HTTP 400/404/405) and background-task failures, as on main.

Technical decisions

The app checks the server’s answers

When the server answers a list request (boat classes, countries, regattas) with something that is not a list, the app now shows an error instead of an empty screen. A login answer without user name or access token is rejected, and if looking up the user fails right after the token arrived, the half-finished login is undone instead of leaving the app half logged in.

We checked in the server’s source code that the current server always sends a list (an empty one is [], never null) and always includes user name and token, so these checks only fire on genuinely broken answers. Checked version: commit ecd97aed of the test server image.

Server code: SecurityResource, BoatClassesResource, CountryCodesResource, and RegattasResource. Older server versions still in use were not checked; see open decisions.

What the logs leave out

Server requests are logged with method, address, status and duration only: no request or response contents, no login headers. Before a line is written, passwords, tokens, user names, e-mail addresses, personal names and device IDs are replaced by [REDACTED], also inside addresses (for example ?secret=[REDACTED] in invitation links). Event, regatta, race and boat identifiers stay readable so support can find the case on the server. QR codes and invitation links are not logged in full. The GPS library’s own log (sent with “Send log to e-mail”) is not filtered; the screen warns about that.

E2E tests first, code-level tests only where E2E cannot reach

Everything a user can do is tested end-to-end on an Android emulator against a real server. Code-level (Jest) tests are kept only for things a UI test cannot trigger reliably: two taps within milliseconds, request timeouts, malformed server answers, a server failing exactly one request in the middle of a multi-step save, polling recovery, and the filtering of credentials out of the logs.

7 · The disposable server and the Android phone

Three containers, one test server

Docker Compose starts Sailing Analytics image main-202609252301, MongoDB 7.0.15, and RabbitMQ 3.13.7. MongoDB stores the disposable database sail_insight_e2e; RabbitMQ serves the server’s messaging channel. The server name and channel are sail-insight-e2e. Only backend HTTP port 8888 is mapped to host loopback.

After the health endpoint responds, provisioning uses the test admin to create the event-creator role, grants SERVER:CREATE_OBJECT for test users, and verifies it. Maestro registers a generated username/email/password through the app. The account is shared across that run, so registration runs first, followed by empty-events and initial boat validation before other journeys create data.

These are intentionally disposable test services. Cleanup removes volumes only for the stack owned by that run; an explicitly reused backend is left running.

How the emulator reaches the server

The target is Android API 36, Google APIs or Play Store; CI uses x86_64 and local Apple Silicon uses arm64. The app is org.sailyachtresearch.sailinsight, built as devDebug with JDK 17. Metro serves the current JavaScript on port 8081. A compatible installed APK can be reused for JavaScript-only work.

ADB reverse maps emulator ports 8888 and 8081 to the host. The development-only backend override directs the app to http://127.0.0.1:8888; production bundles ignore it. Thus the phone talks to the disposable server while Metro supplies the checkout’s code.

Maestro drives the visible Android UI and checks text and control identifiers. The screenshots in this report are taken by the tests themselves. Every run keeps its debug output, the Android log, a screenshot of a failure and a JUnit result.

Run/setup instructions: E2E README · Compose configuration · CI workflow. Existing Metro is reused only with explicit opt-in so the backend override cannot silently point at another checkout.

8 · Open decisions

These changes go beyond fixing a clear bug: each one picks a behavior that the product owner may want differently. Each is implemented as described. The recommendation says whether we would keep it.

  • Archived events can be brought back. On main, archiving removes an event from the list for good (in the app). Now there is an Undo right after archiving and a “Show archived events” switch on the event list. Recommendation: keep. To decide: is archiving meant to be reversible for users?
  • Double taps are blocked for up to 15 seconds. To stop a nervous double tap from starting the same action twice (e.g. two race-count changes, two navigations), a button is locked while its action runs. If something hangs, the lock is released automatically after 15 seconds so the screen does not stay frozen. On a very slow connection an action could take longer than that, and a second tap would then start it again. Recommendation: keep; check the 15 seconds on a real phone with a weak connection.
  • Deleted default marks may come back with a new course. If an organizer deletes one of the default marks (e.g. a start boat) from the mark inventory, it now stays deleted when the inventory is reloaded. But creating a new course still recreates any missing default marks, as on main. Recommendation: keep for now. To decide: should deleting a default mark mean “never create it again”?
  • Saving a course returns before all following races have their copy. When a course is saved and also copied to the following races, the organizer gets the confirmation as soon as the course of the current race is stored. The copies continue in the background; if one of them fails, a separate message says which part failed. Recommendation: keep. To decide: should the organizer rather wait on the screen until every copy is done?
  • Unexpected server answers are treated as errors. If the server answers a list request (boat classes, countries, regattas) with something that is not a list, the app now shows an error instead of an empty screen. The same applies to a login answer without user name or token. This matches the current server code. Recommendation: keep. To decide: do older server versions still in use answer differently (e.g. null for an empty list)?
  • Boat names that differ only in capitals or spaces count as the same. “Wind Rider” and “wind rider ” can no longer exist side by side in My Boats. This prevents accidental duplicates, but blocks two boats whose names differ only in capitalization. Recommendation: keep.
  • “Details” may show the recent log instead of the exact error. Some messages no longer have their original error at hand. For those, Details shows the most recent log lines and says that they may be unrelated. Recommendation: keep.
  • A far-away first position can block tracking and inflate the distance. Found by the regatta test: if the first position after START TRACKING is far away from the next one (here the emulator’s default location in California, then Kiel), the GPS library rejects every following position as a “teleport” (in the test for more than 15 minutes, so no position reached the server), while the Distance tile showed 8,719,855 m (screenshot). On a phone this can happen when the last known position is old, e.g. right after travelling to the venue. The same applies on main; nothing was changed. Recommendation: check on a real phone (e.g. after a long drive to the venue with the app closed) whether tracking recovers; if not, the app could request a fresh position before it starts tracking. Decide whether the Distance tile should ignore such jumps.
  • Log files are visible to the phone’s owner. On Android the log folder can be opened from a computer; on iPhone, the app’s document folder becomes visible in the Files app. Apart from the logs this folder only contains a profile picture saved by the app. The logs contain no passwords or personal data, but they do contain event names and server addresses. Recommendation: keep.

9 · Remaining work

Small findings, not changed

  • Race start right after creating the event: an event starts at the moment it is created, and the time picker only has whole minutes. Setting the first race to “now” within the same minute asks whether to change the event dates, which is confusing. Making new events start at the beginning of the day would avoid it.
  • QR scanner without a working camera: on a device whose camera cannot be opened, the scanner shows “Loading camera…” forever instead of a message.
  • Unreachable screens: Communications, Set Wind and Maneuver Monitor are in the code but no button leads to them. Either remove them or link them.
  • Run the GitHub Actions workflow on GitHub (so far run locally only). The single-phone suite takes about an hour; the two-phone regatta runs separately with ./e2e/regatta.sh.
  • Merge the latest main into this branch before it is merged back.
  • iOS build: fix the Xcode 26 build error in the fmt library (see Latest results), then check on an iPhone that the log folder appears in the Files app.
  • TypeScript reports many existing type errors across the project; they are unrelated to this branch and not fixed here.
  • New texts are translated into English and German; the other languages show the English text.
  • Logout: if stopping the native GPS tracking throws an error, the stored tracking token is not cleared. This is the same as on main and was not changed.
