Sail Insight · UX & network audit

A smoother day on the water

Clearer failures, safer organizer workflows, consistent boat controls, and diagnostics that users can copy. The Android journeys exercise the app against a disposable Sailing Analytics server—not mocked screens.

qa/ux-network-auditAndroid API 36 · Maestro

This branch follows a sailing day: sign in, prepare the regatta, join with a boat, track, and archive. The improvements below retain the app’s existing workflows while correcting failures that were silent, misleading, or left an operation stuck.

Real persisted authentication-error diagnostics contained useful request context and none of the known synthetic credentials. Key boat, expert-settings, and error-details screenshots were refreshed from this run; unchanged and “before” checkpoints remain from branch development. 1 · Signing in: explain what actually failed

A lost connection should not look like a bad password. A failed reset request should not promise an email.

Bug fixed

The form stays usable when the network is gone

Login now distinguishes incorrect credentials from connection failures. The error appears beside the action instead of silently doing nothing. Loading state is released after failure, so the user can retry.

Implementation: the screen uses the actual failure type and status. A synchronous pending flag also prevents the keyboard and button from starting two requests before React updates the loading state. That narrow timing race retains a focused regression test.

Existing journey: auth-login-offline enables airplane mode, submits, checks feedback, then restores connectivity.

Bug fixed

No false “check your inbox”

Password reset now waits for the request. A transport or server failure releases the button and reports the problem. The existing generic confirmation for an unknown account is retained, so the screen does not disclose whether someone has an account.

Existing journey: auth-password-reset-offline. The code checks additionally cover the simultaneous-submit race; no duplicate UI test suite is needed for the ordinary offline screen.

2 · Preparing a regatta without losing the organizer’s work

The form should reveal the field that needs attention. Saving a course and changing race counts should leave server and screen in agreement.

UX improved

Show the problem where it can be fixed

Submitting an incomplete event scrolls toward the invalid section. The missing venue is marked directly below its field. Backend failures likewise scroll into view rather than staying below the keyboard or screen edge.

Implementation: section positions are measured by the existing form. Discard thresholds must be ordered; boat and event required fields reject whitespace-only input.

Existing journey: create-event-validation checks missing venue feedback.

UX improved

The keyboard no longer hides the choice

Focusing the boat-class field scrolls it upward and reserves enough space for the suggestions. Create Event reuses the list it already fetched rather than asking the same input to fetch it again.

Evidence: this recorded Android checkpoint shows all five suggestions above the keyboard. It is visual evidence, not a new automated alignment or pixel-analysis test.

Bug fixed

A failed create is not a stuck spinner

The create state is cleared on failure. If the server created the event but a later setup step failed, the app distinguishes that partial result from a failed creation, reducing the risk of creating a duplicate on retry.

Verification: create-event-offline checks connection feedback and recovery. Partial post-create failures retain lower-level tests because the existing disposable server does not expose a reliable switch for failing exactly the next setup request.

Bug fixedUX improved

Race-count changes are deliberate and ordered

Reducing the count names the races that will be permanently deleted. Rapid changes are queued and calculated against refreshed server state, rather than repeatedly using an outdated local count.

Implementation: overlapping settings saves are counted, so one completed request cannot re-enable controls while another is still running. Tracking starts after settings are saved. define-races checks adding, cancelling deletion, confirming deletion, and reopening the overview; concurrency and partial-write failures retain focused code checks.

Bug fixed

Save means the course can be reopened

The editor starts and stops local location updates on focus. Ping rejects missing or non-finite coordinates instead of submitting an empty position. Manual degrees/minutes input is checked against coordinate bounds.

Repeated Save presses no longer create duplicate courses. Copying the saved course to following races is separate from the main save; a partial copy failure gets a partial-success message, not an unqualified success.

Existing journey: define-course pings, saves, and reopens the course. These three recorded checkpoints show the intended sequence. They do not prove real-world GPS accuracy, background tracking, or all propagation failures.

Bug fixed

An inventory refresh should not undo deletion

The inventory screen reloads without recreating missing default marks. A refused server deletion restores the locally removed item and reports the error. Failed inventory retrieval is not treated as an empty inventory that needs every default recreated.

Existing journey: mark-inventory deletes, reloads, and restarts to check the mark stays absent. The screenshot alone is not proof of persistence. Course setup can still create missing defaults; that distinction is called out for Axel below.

3 · Joining, tracking, and reporting a problem

Competitor forms stay simple. Technical information stays optional.

Bug fixed

Accept usable boat data, not just nonempty strings

Boat names and sail numbers are trimmed. Required fields reject blank input. Duplicate-name checks account for surrounding spaces and letter case. Handicap validation rejects non-finite and non-positive values.

Deleting after editing a name without saving still targets the original stored boat. A failed deletion is shown rather than leaving the user to guess what happened.

Existing journeys: competitor-boat-validation checks invalid then valid boat entry; my-boats checks adding and deletion after an unsaved rename.

UX improved

Use the same button as the rest of the app

The old custom text used different typography and sat too low. NEW BOAT now uses TextButton and the standard primary-button font. Using the shared component keeps typography and vertical alignment consistent with the other actions.

Evidence: this final-run screenshot shows the shared button with consistent typography and centered text. The existing boat journey passed. Earlier boat-list screenshots with the old button were not used here.

Bug fixed

Start once; report stop failures honestly

Tracking focus handling is idempotent, including the first focus. Repeated actions are guarded, and switching away from another tracked event asks for confirmation. A failed stop no longer displays the event-finished success message.

GPS decision: the speculative 60-knot distance filter was removed. Distance again uses the SDK odometer directly. Unverified ping accuracy, sample-count, and cache-age overrides were also removed; ping still awaits the SDK callback using its established defaults. Raw GPS email export remains unfiltered and its existing API is unchanged. competitor-tracking checks the joined list and start/stop screens—not accuracy on the water.

Bug fixed

A failed refresh should not stop later updates

Polling avoids offline requests and resumes after failed or missing responses. A failure streak produces feedback without repeating the same snackbar on every poll.

Evidence boundary: leaderboard opens and refreshes this screen. The screenshot contains no populated race results; it does not prove ranking correctness. Retry behavior is covered by focused polling tests.

New app behavior

Archiving is reversible

The active list can be cleared without losing access to archived events. Undo and the archived view offer a route back. A server failure restores the previous local archive state.

Existing journey: archive-event checks hiding and restoration. Axel should review the archive/restore interaction as a product choice, rather than treating it as only a technical fix.

UX improvedNew diagnostics UI

Readable first, technical when requested

A real duplicate-event response produces a useful message. Expert users can expand its method, endpoint, status, and backend error code, then copy the details.

Existing journey, improved: create-event-error-details checks normal-user visibility, expanded/collapsed details, and copy confirmation. Inspection of the application’s actual logs is a separate verification step, not a reason to hide synthetic event names.

New app behavior

Give support the error, not a photograph of it

Enable: Account → Settings → tap the version number 15 times → enable Show technical error details. Reproduce the failure, expand Show details, and choose Copy technical details.

Copy local diagnostics collects recent app history without requiring verbose GPS logging. Copying does not upload the report; sharing it remains the user’s action. If a snackbar no longer has its original exception, its Details action explicitly labels the result as recent history—not necessarily the cause of that failure.

Existing added journey: expert-local-diagnostics checks GPS-switch persistence and the copy action. It first submits an incorrect password, then logs in without clearing app data. Copy must succeed with real persisted HTTP-error history; the empty-state message no longer passes the journey. No artificial startup log is needed. GPS email export is separate and remains raw; the screen warns before sharing.

Technical decisions · simpler, not merely more defensive

Backend contracts were checked in the server code

The running test server identifies commit ecd97aed037630f54192832b84517e0fd4de3516. At that commit, the three endpoints used by the app’s shared list handler—boat classes, country codes, and regattas—construct JSON arrays. An empty result is [], not null. The single array check is therefore retained; malformed successful responses are failures rather than silently empty screens.

The security server returns username for a successful user response and access_token for token issuance. Missing required values are rejected before incomplete authentication state can be accepted. A failed user lookup after token issuance clears the partial login. User validation was reduced to the required username check.

Source: SecurityResource, BoatClassesResource, CountryCodesResource, and RegattasResource. This establishes the inspected server version, not every historical backend.

Production diagnostics record less sensitive data

Network logs record method, URL, status, and failure type—not request bodies, authorization headers, or authentication responses. API exceptions in local history and Crashlytics keep request context rather than raw backend bodies that may echo user input. QR payloads and full deep-link parameters are not logged.

A small shared boundary removes actual credential and personal/device fields, URL credentials, sensitive query values, and bearer/basic tokens. Event and race identifiers remain available for support. Serialization happens once for Logger output; storage, display, and copying do not repeatedly sanitize the same data. Local history has bounded writes, retention, and a bounded copy size. The raw GPS export is not passed through this filter.

Removed: custom per-flow privacy gates, artifact withholding, JUnit aggregation, and artificial bootstrap logging. Maestro now runs normally and keeps its debugging artifacts. Synthetic test data is not redacted from test screenshots or test artifacts.

Keep tests where they add independent evidence

Mock-heavy UI tests for error expansion, settings, ordinary authentication feedback, form validation, and archive selectors were removed where Android journeys are the better verification route. Focused tests remain for submission and save timing races, timeouts/abort behavior, malformed backend responses, partial write failures, polling recovery, and production diagnostic serialization. These are difficult to force reliably through the existing UI/backend setup.

The full audit considered both the QA commits since merge-base 6b1d9b7c and the inherited working tree. Organizer improvements were retained; no unapproved product rollback was used to make the diff smaller.

5 · The disposable server and the Android phone

Three containers, one test server

Docker Compose starts Sailing Analytics image main-202609252301, MongoDB 7.0.15, and RabbitMQ 3.13.7. MongoDB stores the disposable database sail_insight_e2e; RabbitMQ serves the server’s messaging channel. The server name and channel are sail-insight-e2e. Only backend HTTP port 8888 is mapped to host loopback.

After the health endpoint responds, provisioning uses the test admin to create the event-creator role, grants SERVER:CREATE_OBJECT for test users, and verifies it. Maestro registers a generated username/email/password through the app. The account is shared across that run, so registration runs first, followed by empty-events and initial boat validation before other journeys create data.

These are intentionally disposable test services. Cleanup removes volumes only for the stack owned by that run; an explicitly reused backend is left running.

How the emulator reaches the server

The target is Android API 36, Google APIs or Play Store; CI uses x86_64 and local Apple Silicon uses arm64. The app is org.sailyachtresearch.sailinsight, built as devDebug with JDK 17. Metro serves the current JavaScript on port 8081. A compatible installed APK can be reused for JavaScript-only work.

ADB reverse maps emulator ports 8888 and 8081 to the host. The development-only backend override directs the app to http://127.0.0.1:8888; production bundles ignore it. Thus the phone talks to the disposable server while Metro supplies the checkout’s code.

Maestro drives the visible Android UI and checks text and control identifiers. Its screenshot commands produce the illustrated checkpoints; failures retain debug output, logcat, a screenshot, and JUnit. A single suite invocation uses the normal Maestro configuration—no custom privacy gate or artifact suppression.

Run/setup instructions: E2E README · Compose configuration · CI workflow. Existing Metro is reused only with explicit opt-in so the backend override cannot silently point at another checkout.

6 · Choices for Axel’s review

  • Archive/restore: retain the reversible archive interaction shown above. It adds an archived view and undo action, rather than only hiding an event. Recommendation: keep, subject to Axel’s workflow review.
  • Race deletion and repeated actions: retain explicit permanent-deletion confirmation and serialized count changes. The shared navigation guard also has a one-second cooldown and a 15-second safety release. A long-running operation could outlive that release; recommendation: review these timings on a real device before changing behavior. No silent rollback was made.
  • Default marks: inventory refresh respects deletion, but course setup may recreate missing default marks. Recommendation: keep that existing course behavior for now; Axel should decide whether deletion should also suppress later default creation.
  • Course propagation: saving the primary course no longer waits for all following-race copies. Partial copy failure is reported separately. Recommendation: keep the faster return, but confirm whether organizers want to remain in the editor until every copy finishes.
  • Backend compatibility: the inspected server returns arrays, usernames, and tokens as required. Recommendation: retain the single contract checks. If older deployed servers intentionally return null collections, review those versions before changing compatibility policy.
  • Boat-name matching: surrounding spaces and letter case now count as the same name. This prevents near-duplicates but disallows two boats that differ only by capitalization. Recommendation: review this rule with Axel before changing it.
  • Recent diagnostic history: it is explicitly distinguished from the original exception and may contain unrelated earlier failures. Recommendation: keep this support aid, with that distinction visible.

No approval is being inferred for these product choices. The authorized GPS heuristic removal has already been made; no new GPS acceptance heuristic was substituted.
